# The public demo

A deployment of LOOP that anyone can click into, with a **Explore as
Proprietor** / **Explore as Service Engineer** option under the ordinary
sign-in form.

The demo runs the same code as the real instance. The only differences are one
environment variable and the database it points at.

---

## 1. How it is kept separate from the real data

The demo has **its own PostgreSQL**, containing nothing but the fictional
records created by `scripts/manage.py seed-demo` (invented customers like
"Sunrise Textiles", invented quotations, invented engineers). The real
Arcot data stays on the laptop and is never uploaded, so there is nothing to
leak and no schema change was needed to keep the two apart.

`DEMO_MODE` is the switch:

| `DEMO_MODE` | Sign-in page | `POST /login/demo` | `seed-demo` |
|---|---|---|---|
| `false` (default, laptop) | unchanged — no demo options rendered | `404` | refuses to run |
| `true` (demo deployment) | demo options shown | signs in | runs |

The demo personas are ordinary `users` rows with the ordinary `PROPRIETOR` and
`SERVICE_ENGINEER` roles and hashed passwords. The demo button issues a token
through `AuthService` exactly as a typed password does, so every authorization
rule applies to demo visitors unchanged — a demo engineer still cannot reach
`/quotations`.

Files involved:

| Concern | File |
|---|---|
| Which personas are offered | `app/demo/accounts.py` |
| The sample data | `app/demo/seed.py` |
| Signing in as a persona | `app/services/demo_service.py` |
| The buttons | `app/web/templates/auth/login.html` |
| The "demo data" strip | `app/web/templates/base.html` + `demo_reset_note` in `app/config.py` |

Adding a third persona is one entry in `DEMO_ACCOUNTS` — no route or template
change.

## 2. Database — Supabase

Supabase is used **only as a hosted PostgreSQL**. LOOP does not use Supabase
Auth, Storage or any Supabase client library; it needs a `DATABASE_URL` and
nothing else. Any PostgreSQL would do.

1. Create a project at <https://supabase.com>. Note the database password.
2. **Connect → Session pooler**, and copy that connection string.
3. Rewrite it for SQLAlchemy + psycopg 3:

   ```
   postgresql+psycopg://postgres.<ref>:<password>@<host>:5432/postgres?sslmode=require
   ```

   Note `postgresql+psycopg://`, not `postgresql://`.

> **Use the session pooler, not the transaction pooler on port 6543.** psycopg 3
> uses prepared statements, which pgbouncer in transaction mode does not
> support; you would see intermittent `prepared statement ... does not exist`
> errors under load.

## 3. Web service — Render

`render.yaml` in the repository root describes the service. Render builds the
existing `Dockerfile` and starts it with `scripts/start.sh`, which runs
`alembic upgrade head` before serving, so a deploy never serves traffic against
an unmigrated schema.

1. Render → **New → Blueprint**, point it at this repository and the branch
   holding the demo.
2. When prompted, fill in the two values marked `sync: false`:
   - `DATABASE_URL` — the Supabase string from step 2
   - `DEMO_PASSWORD` — any strong password; it is what the seeded accounts get
3. `JWT_SECRET` is generated by Render. `DEMO_MODE=true` and
   `APP_ENV=production` are already in the blueprint — `APP_ENV=production` is
   also what makes the session cookie `Secure`.
4. Deploy, then check `https://<service>.onrender.com/health` returns
   `{"status":"ok","app":"LOOP"}`.

### Seed it once

The first deploy creates the tables but does not fill them. Seed from your own
machine, pointing at the Supabase database:

```sh
DEMO_MODE=true \
DEMO_PASSWORD='<the same value you set on Render>' \
DATABASE_URL='<the Supabase URL>' \
  python scripts/manage.py seed-demo
```

Environment variables take priority over `.env`, so this does not disturb your
local configuration. Check `DATABASE_URL` before running it — `--reset` deletes
data, and the only thing standing between this command and the wrong database
is the value you paste here.

> Render's **Shell** tab would be the obvious place to run this, but shell
> access is not included on the free instance type. Seeding from your machine
> works on any plan.

Reload the sign-in page; the demo options are there.

## 4. Keeping it clean — the reset

Visitors can create and edit freely, so the demo drifts. `.github/workflows/demo-reset.yml`
wipes and reseeds it nightly (20:30 UTC / 02:00 IST), and can also be run on
demand from the repository's **Actions** tab.

Repository secrets to add under **Settings → Secrets and variables → Actions**:

| Secret | Value |
|---|---|
| `DEMO_DATABASE_URL` | the same string as `DATABASE_URL` on Render |
| `DEMO_PASSWORD` | the same value as on Render |

> **Scheduled workflows only run from the repository's default branch.** While
> the demo lives on its own branch, use the manual **Run workflow** button; the
> nightly schedule starts once the branch is merged into `main`.

To reset by hand from anywhere with the connection string:

```sh
DEMO_MODE=true DEMO_PASSWORD=... DATABASE_URL=... \
  python scripts/manage.py seed-demo --reset
```

`seed-demo` without `--reset` is idempotent, so running it twice is harmless.

## 5. Free-tier behaviour worth knowing

- **Render free web services sleep after ~15 minutes idle.** The first request
  after that takes roughly 30–50 seconds while the container wakes. Fine for a
  demo; worth warning someone before you send the link.
- **Supabase free projects pause after ~7 days with no activity** and must be
  resumed from the dashboard. The nightly reset workflow counts as activity, so
  once it is running on `main` the project stays awake on its own.

## 6. Running the demo locally

```sh
# in .env
DEMO_MODE=true
DEMO_PASSWORD=some-local-password
```

```sh
python scripts/manage.py seed-demo --reset
uvicorn app.main:app --reload
```

Then open <http://localhost:8000/login>. Set `DEMO_MODE=false` again to get the
ordinary sign-in page back.
